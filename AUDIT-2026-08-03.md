## A. Correctness against the live MailKite API

### A1 — The signing secret is handed to us and we ignore it *(high)*
`PUT /api/domains/:id/webhook` returns `{ domain, webhookUrl, ackMode, routeId, signingSecret }`
(`api/src/index.ts:2438`). `hooks.activate()` destructures only `webhookUrl`
(`new-inbound-email.mjs:49`), so the user is asked to paste the secret by hand into an
**optional** `webhookSecret` prop — meaning the default deployment verifies nothing.

**Fix:** persist `signingSecret` to `this.db` in `activate()` and use it in `run()`; keep the
prop only as an override. Signature verification becomes always-on with zero user steps.

### A2 — No replay window on the signature *(high)*
The canonical verifier (`sdks/node/index.js:417-442`) rejects any event where
`|Date.now() - t| > 5 * 60 * 1000` (`DEFAULT_TOLERANCE_MS`, line 23). `verifySignature()`
(`new-inbound-email.mjs:65-82`) parses `t` but never checks its age → a captured delivery
replays forever. It also compares `Buffer.from(hexString)` (ASCII bytes) where the SDK compares
`Buffer.from(hex, "hex")` (decoded bytes); both are constant-time and equivalent in effect, but
mirror the SDK so there is one algorithm to reason about.

### A3 — activate/deactivate silently destroy a pre-existing webhook *(high)*
A MailKite domain has **one** catch-all `*@domain` webhook route ("one webhook per domain",
`api/src/index.ts:2403-2404`). `activate()` issues a PUT that *replaces* it, and `deactivate()`
issues an unconditional DELETE (`new-inbound-email.mjs:48-62`). So deploying this source
silently detaches whatever the user already had wired, and deleting the source removes their
webhook entirely rather than restoring it.

**Fix:** `GET /api/domains` already returns `webhookUrl` + `webhookAckMode` per domain
(`api/src/index.ts:2229-2233`) — read the incumbent in `activate()`, stash it in `db`, and in
`deactivate()` restore it (PUT) instead of DELETE when one existed. Say so in the source
description either way; this is the kind of thing registry reviewers catch.

### A4 — `test-event.mjs` has drifted from the payload contract *(medium)*
`buildWebhookPayload()` (`api/src/index.ts:9684-9707`) emits `receivedAt` (epoch ms) **and**
`receivedAtIso`; the sample has neither. `from`/`to` entries carry `name` when the MIME header
names the same address — the sample shows `address` only. The registry renders this file as the
event shape users build against, so drift here is user-visible.

### A5 — Send Email exposes 10 of the 17 supported body fields *(medium)*
`SendBody` (`api/src/index.ts:4750-4781`) also accepts `attachments`, `headers`, `inReplyTo`,
`scheduledAt`, `trackOpens`, `trackClicks`, `attribution`. None are props. `scheduledAt` in
particular changes the response to `{ id, status: "scheduled", scheduledAt }`
(`api/src/index.ts:4995`), while `$summary` (`send-email.mjs:93`) always says "Sent" — it should
read `response.status`.

### A6 — Assumptions that CHECK OUT (do not "fix" these)
- `GET /api/domains` is a bare array of rows with `mx_verified` (`api/src/index.ts:2229`) — the
  domain picker's filter and shape are right.
- `requireAuth` accepts an `mk_live_…` API key on `/api/domains*`, not just a session token
  (`api/src/auth/middleware.ts:49-67`; `app.use('/api/domains', requireAuth)` at `index.ts:1470`),
  so an API-key connected account can register webhooks. The spec's `"auth": "Session token"`
  label on those methods is a docs-side simplification, not a restriction.
- `POST /v1/send` accepts `to`/`cc`/`bcc` as arrays (`index.ts:4752-4757`) and returns
  `{ id, status }` — the action's payload and `response.id` usage are correct.
- Ack-mode body `{"status":"ok"}` matches `MailKite.replyOk()` (`sdks/node/index.js:451-453`).
- A domain-scoped key sees exactly one domain in the picker (`index.ts:2213`) — correct, but
  worth a line in the README so it doesn't read as a bug.

## B. Registry-guideline compliance

| # | Rule (quoted) | Us | Fix |
|---|---|---|---|
| B1 | "Source keys should use past tense verbs describing the event (e.g. `linear_app-issue-created-instant`)" | `mailkite-new-inbound-email` | → `mailkite-email-received-instant`. Display name "New Inbound Email (Instant)" already fits the *name* rule and stays. |
| B2 | "All registry components should include an `annotations` object with `destructiveHint`, `openWorldHint`, `readOnlyHint`" | action has it, **source does not** | add to the source |
| B3 | "webhook sources should fetch existing events in the `deploy()` hook, limited to 50 events maximum" | no `deploy()` hook at all | see below |
| B4 | app file should contain "API methods with JSDoc documentation" | `//` line comments only | convert the 5 methods in `mailkite.app.mjs` to JSDoc |
| B5 | "Modify the package `version` each time you change app file code or dependencies" | `0.0.1`, untouched | fine for the first PR; bump on every app-file edit from now on |

**B3 detail (the only non-trivial one).** `GET /api/messages` returns a bare array, newest
first, with `limit` (1–200) and a `before` cursor (`api/src/index.ts:4166-4191`). Two catches:
there is **no domain filter** — only a `search` substring — so filter client-side on the `to`
domain; and list rows are **not** webhook payloads (snake_case `text_body`/`html_body`/
`thread_id`/`received_at`/`spf`/`dkim`, structured `from`/`to` via `withStructuredAddresses`
at `index.ts:4153-4164`, no `type`, no `attachments` — those need `GET /api/messages/{id}`).
So `deploy()` needs a row→`email.received` mapper, and that mapper is the natural place for the
first unit test.
